## 2. 基本原則

1. **一件事只有一個負責方**。第 3 節「負責」欄只寫一方；其他方是「協助」或「提供」。
2. **文件正本只有一份**：三份規格文件（專案總覽、助理技能、官網規格）、決策紀錄、串接規格、本協議，正本在 GitHub 的 `docs/`，由**開發**維護。好事道 AI 發現問題或需要修改時，**提出問題，不直接改副本**；開發改完正本後，由 Bill 重新上傳到好事道。
3. **看板只有一份**：專案 150 看板由**好事道 AI** 建立與維護（新增、刪除、改日期、改負責角色）。
   - 開發的進度**預設透過 Bill 回報**給好事道 AI 更新。
   - Bill 另外書面同意後，開發可以直接更新**自己負責任務的狀態與一句說明**，不新增、不刪除任務，也不改日期。
4. **資料以物資平台為準**：捐贈、需求、庫存、配送的資料只存在物資平台後台。官網與助理都透過 API 讀寫，不另外存一份。
5. **佔位清單由好事道 AI 維護**：假名稱、假網址只用在官網草稿；規格文件維持變數寫法（例如 `{捐款網址}`），不寫入假值。每個佔位值由清單中「由誰提供」的一方負責給正式值。
6. **不編造**：雙方都不自行編造數字、單位名稱、聯絡資料；沒有的資料列入「待確認」。個人電話（例如荃安理事長的手機）不可以當成協會服務電話公開。
7. **標示「暫定」的項目**：與 Mason 有關的期限和子網域都標「暫定，待 Mason 確認」。暫定不影響本協議生效，也不影響建看板；Mason 確認後由好事道 AI 更新看板，有變動時通知開發。

## 5. 變更與溝通流程

1. **發現規格問題**：好事道 AI 列出問題（哪份文件、哪一節、問題是什麼）→ Bill 轉給開發 → 開發修正正本並說明改了什麼 → Bill 重新上傳。
2. **需要決策**：任一方都不自行決定，列出選項和建議，交給 Bill 決定；決定記入《需求決策紀錄》（開發維護）。
3. **進度回報**：
   - 好事道 AI：直接在看板更新自己負責的任務。
   - 開發：依第 2 節第 3 點，預設透過 Bill 回報；Bill 同意後可直接更新自己任務的狀態。
   - 任何一方預期延誤時，在原定日期**至少 3 天前**提出，說明原因與新日期，由 Bill 決定是否調整。
4. **衝突處理**：兩方對同一件事有不同做法時，以第 3 節的「負責」方為準；仍有爭議由 Bill 決定。
