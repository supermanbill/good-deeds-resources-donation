## 2. 基本原則

1. **一件事只有一個負責方**。表格中「負責」欄只寫一方；其他方是「協助」或「提供」。
2. **文件正本只有一份**：三份規格文件（專案總覽、助理技能、官網規格）、決策紀錄、串接規格，正本在 GitHub 的 `docs/`，由**開發**維護。好事道 AI 發現問題或需要修改時，**提出問題，不直接改副本**；開發改完正本後，由 Bill 重新上傳到好事道。
3. **看板只有一份**：專案 150 看板由**好事道 AI** 建立與維護。開發完成或延誤時，透過 Bill 回報；或經 Bill 同意後，由開發直接更新自己負責任務的狀態（不新增、不刪除任務）。
4. **資料以物資平台為準**：捐贈、需求、庫存、配送的資料只存在物資平台後台。官網與助理都透過 API 讀寫，不另外存一份。
5. **佔位清單由好事道 AI 維護**；每個佔位值由「上線前換成」欄的提供方負責給正式值。
6. **不編造**：雙方都不自行編造數字、單位名稱、聯絡資料；沒有的資料列入「待確認」。

## 5. 變更與溝通流程

1. **發現規格問題**：好事道 AI 列出問題（哪份文件、哪一節、問題是什麼）→ Bill 轉給開發 → 開發修正正本並說明改了什麼 → Bill 重新上傳。
2. **需要決策**：任一方都不自行決定，列出選項和建議，交給 Bill 決定；決定記入《需求決策紀錄》（開發維護）。
3. **進度回報**：雙方完成或延誤時，在看板對應任務更新狀態並寫一句說明。
4. **衝突處理**：兩方對同一件事有不同做法時，以本協議第 3 節的「負責」方為準；仍有爭議由 Bill 決定。
